# 情報の優先度と文書の役割

更新：2026-11-25。4領域（ケース①/ケース②/フェルミ①/フェルミ②）ごとに、inputと学習で得た情報を文書へ保存する。現在の登録内容・進捗は各INDEX・INPUT・LEARNING・READINESSを参照する。

## 文書を分ける

| 文書 | 目的と載せる範囲 | 正本との関係 |
| --- | --- | --- |
| CORE.md | 現在採用済みのA情報の重要な要約。短く構造を示す | 詳細へのリンク・条件・更新日を持つ表示層 |
| INDEX.md | 保管した全情報をA→B→Cで索引化 | 全件のID・優先度・状態・詳細・根拠・履歴を追える |
| details/ | 情報の種類ごとの詳細本文 | 情報本文の正本。共通知識はsharedを参照 |
| references/（フェルミ①） | 条件付き数字設定例の参照層。NUMBER_INDEXから用途別へ | 基礎概数/方法/演習ログとは別。個別行IDは知識カード数や演習数へ加算しない |
| HISTORY.md | その領域の議論・変更への入口 | 日付付きログへの参照と、変更IDの索引 |
| INPUT.md | 教材・資料・input対象の索引 | 原資料台帳と資料ノートへの入口 |
| LEARNING.md | 演習・照合・改善の進め方と索引 | 実施後のlearning記録へつなぐ |
| CURRENT.md | 現在読むべき文書の案内 | CORE/INDEXへ誘導し、採用情報を二重管理しない |

①の反復学習には、[SOLVE_WORKFLOW](learning/SOLVE_WORKFLOW.md)（実行手順）、[COVERAGE](learning/COVERAGE.md)（情報種類・問題型の網羅範囲と不足）、[CYCLES](learning/CYCLES.md)（inputと演習を結ぶ履歴・再開点）を使う。これらは進め方・管理の文書であり、知識本文や全回答の別の正本にしない。

Notionでは、各領域のホームを「重要情報の要約」とし、子ページに全情報索引、種類別の詳細、議論・変更履歴を置く。GitHubはCodex向け詳細、Notionは本人向けに重要なエッセンスと構造を短く可視化する。双方に別の独立した正本を作らず、情報ID・参照先で結ぶ。

## 優先度は3段階

| 優先度 | 意味 | 判定の観点 |
| --- | --- | --- |
| A 必須 | 欠けると回答全体または支援の品質を大きく損なう情報 | 基本原則、広い適用範囲、重大な誤りの防止、重要な検証済み改善 |
| B 重要 | 特定の問題・場面で必要になる情報 | 問題種類ごとの解法・知識・対応、適用条件付きの改善 |
| C 補足 | 理解や選択肢を広げる詳細 | 応用事例、比較材料、追加説明等 |

頻度だけで決めず、誤った場合の影響・適用範囲・実際の評価を考慮する。各情報に優先度の理由を記す。優先度を変更した場合も、旧/新・理由・根拠を履歴へ残す。

**優先度と確からしさは別軸。** 状態は候補/未確認/採用済み/保留/失効等で管理する。Aでも未確認の情報をCOREの採用済み情報へ混ぜない。架空のA情報や学習成果を作らない。②で本人が合意した現行仕様は「仕様として採用」と明示し、効果/速度が検証済みかを別に示す。教材・演習先の利用優先度は情報項目のA/B/Cとは別に台帳へ記録する。

## 全情報の索引に載せる項目

情報ID、短い要点、種類、モードと①②、A/B/C、優先度の理由、状態、適用条件、出典と確認日、学習・評価の根拠、詳細本文、変更履歴、後継ID。登録した情報は優先度が低くても索引から漏らさない。失効情報も状態と後継への参照を保持し、現行として読まれないようにする。

全情報とは、すべての本文を1つの巨大文書へ複製することではなく、全項目へ索引から漏れなく到達できる状態。原資料や議論の全文は、それぞれの適切な保存先へ置く。

INDEXの「採用済み」の項目をA→B→Cでたどると、現在使う情報の全体へ到達する。候補・未確認・保留・失効は状態を明示し、現行体系と混ぜない。資料・比較ノートはINPUT、全演習はLEARNING、議論はHISTORYに漏れなく索引化し、INDEXからも各入口へつなぐ。未整理の重要な発見を出典ログの中だけに埋めない。

必要な方法が候補にある場合は、候補の条件・根拠・未評価/例外まで読む。適用できるなら候補ID/版と仮定・留保を明記して検討/使用し、正式採用と扱わない。「採用済みだけ読んだ」ことを全問題に必要な理解の復元としない。特に方法選択の枝、未観測の係数、原因仮説は採否と使用条件を分ける。

## 情報が足りるかを判断する

ID数、ファイル数、演習数、数値の個数は別の単位。複数の関連数値を1カードにまとめたものと、1つの方法の枝を1件と数える場合を明示し、重複参照する共通知識を合算しない。件数の増加を精度向上としない。現在の監査/不足は[情報監査](learning/audits/2026-11-26-information-audit.md)、実際の範囲と精度はCOVERAGE/READINESSへ。

| 観点 | 保存する最低限の内容 |
| --- | --- |
| 解法・知識 | 何の問いで選ぶか、手順/式、外れる条件と代替、典型的な誤り、根拠、情報ID/版/採否 |
| 概数・係数 | 元の観測と分母/時点/単位、計算用の丸め、設問への橋渡し、感度等の幅の性質、適用不可、必要時の再探索/見直し条件 |
| 施策・事例 | 原因条件→作用→実施主体/資源/費用→成果/指標→副作用/反証。企業報告の事実と、他社への転用/因果効果を分離 |
| 演習からの抽出 | 重要な一致/誤り/不足と原因、維持/修正、不採用理由、再利用本文への反映IDと版、別問での結果/次の確認 |
| 引継ぎ | 最新の読む順、採用/候補と未対応、全索引への到達、本文と証拠の関係、更新日。過去の現在地を入口へ重複固定しない |

各学習単位の記録時に、上のどこが不足していたかを確認する。適切な情報が本文にあるなら件数を増やさず参照/証拠を補う。重要な発見が原回答だけにあるなら適用条件付きで本文へ抽出し、根拠がない一般化は候補/未確認として残す。定期的な無目的更新を増やす意味ではない。

## 種類によるグループ化

- ケース①：解法・問題分類、分析と論拠、施策・事例、検証と結論。
- フェルミ①：解法・分解、基礎概数/定義、数字設定方法、条件付き設定例の参照索引、式と計算、妥当性確認。設定例が掲載されていることと、唯一の最適値/観測値であることを分ける。
- ケース②：入力の読取、初手の切り出しと表示、途中依頼への適応、本人の評価。
- フェルミ②：上位の本番順序、その配下で準備時の確認と、お題受領〜初回共有を独立させる。本人評価/対話証拠は別。初回後の追加依頼の具体的対応は未議論として保留。

具体的な詳細文書は情報が生じてから追加する。共通の概数・解法等を重複して全文保存せず、1つの本文へ複数領域から参照する。

input/は「誰が何を述べたか」と比較・統合に至る過程、learning/は問題ごとの自作回答と評価の証拠。現在再利用する本文はdetails/またはshared/knowledgeに整理する。採用時は適用条件・根拠・検証範囲・未解決点を残し、情報の性質に合う確認を行う。ひな形の空欄は採用済み情報へ数えない。

## 更新と新チャットでの利用

input/演習の記録 → 詳細本文と評価根拠の整理 → INDEXへ全件登録 → 採用済みAだけCOREへ要約 → Notionの対応箇所へ反映 → リンク・意味・状態を照合する。議論・変更は日付付きlogsへ、領域別HISTORYから参照する。

準備時はCOREを先に読むが、それだけで十分な理解を得たと見なさない。INDEXで全体の分類・適用範囲を把握し、必要なB/CやAの詳細も読む。優先度は読む順・要約範囲の目安であり、①の解く範囲を削るものではない。

ひな形は[templates](templates/README.md)。編集境界と承認を重ねない運用は[OPERATIONS](OPERATIONS.md)を併用する。
